## Secuencia de creación y alcance de la callback

1. `ActorService::create_actor` pasa `params->create_function` a `fopAcM_create` y devuelve el ID de solicitud (actor.cpp 220–236).
2. `fopAcM_create` genera append y pasa callback a `fpcM_Create` ([mng.cpp258–268](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/f_op/f_op_actor_mng.cpp#L258)). El inline convierte la firma a `stdCreateFunc` y envía userdata NULL ([manager.h45–48](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/include/f_pc/f_pc_manager.h#L45)); el header de esta última declara `int (*)(void*,void*)`. Se registra la implementación oficial, sin inventar firma/contexto adicional para el mod.
3. La tabla de fases ordena SubCreateProcess → IsComplete → PostMethod. SubCreate llama al método nativo; `fpcBs_SubCreate` avanza al completarse el create ([base.cpp179–198](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/f_pc/f_pc_base.cpp#L179)). PostMethod invoca la función sobre ESA solicitud; si retorna 0 vuelve a esperar, no garantiza ejecución única ([stdcreate_req.cpp67–109,148–177](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/f_pc/f_pc_stdcreate_req.cpp#L67)).
4. E_OC ya asignó `field_0x560 = health = 40/220` y llamó `daE_OC_Execute(this)` dentro de create antes de devolver phase. Una escritura prematura se sobrescribiría; un postmethod estándar sería posterior a esa inicialización/primera Execute, pero sigue siendo escritura directa sin setter autorizado.
5. El actor añadido por StageService toma otra ruta: stage_create_new_actors → dStage_actorCreate → **`fopAcM_Create(actorInf->procname,NULL,i_actorPrm)`** ([d_stage.cpp1635–1662](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/d/d_stage.cpp#L1635),2611–2635). No envía callback CP03 ni devuelve ActorId al servicio. Crear además por ActorService produciría una segunda solicitud, no adaptaría la existente.

Esta secuencia es evidencia estática del host fijado, no prueba fake de una callback que el host no llama, ni una ejecución real. El análisis se detiene aquí: no se reabre el bloqueo histórico independiente de descarga de perfiles DLL.

## Decisión R1–R8

R1 y R3–R6 se pueden conservar en el preset StageService existente de CP02, pero R2 no se satisface: salud 220, no 150. El camino ActorService postmethod aporta una identidad de solicitud y un momento pertinente, pero no aporta operación HP autorizada (R7/R8) ni correlación con StageService. Incluso admitiendo una asignación tipada en la callback, no hay garantía acreditada de revocación/cancelación de esa solicitud antes del unload. Un actor propio no acredita R4 sin la adaptación/clonación prohibida. Por tanto **NO-GO para implementación/entrega CP03 bajo las restricciones actuales**. No hay mod, build ni artefacto CP03.
