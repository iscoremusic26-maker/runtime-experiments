# Recursos, archivos, ARC y overlays

Fuente: `TwilitRealm/dusklight@40457c6adb381928e4b5fef6ed459ed291edd5e2`. Objetivo: Dusklight 2.0.3, Windows x64, DX12, GZ2E01. Esta ficha registra inspección estática; no se ejecutó el juego ni un mod. Los símbolos del juego que aparecen aquí no tienen disponibilidad de enlace ni hook demostrada por su mera existencia.

## Límites y dos contratos distintos

`ResourceService` sirve exclusivamente el árbol `res/` del propio bundle. `load` requiere `ResourceBuffer.struct_size`, valida ruta relativa y copia bytes a una allocation registrada por mod; archivo vacío produce `data=null,size=0`. No monta un ARC ni obtiene automáticamente recursos del disco. `free` comprueba ownership; detach reclama allocations pendientes. Reutilizar un out-buffer sin liberarlo antes pierde la referencia del mod aunque el host conserve el registro. **STATIC_CROSSCHECKED, PRES-001**: [sdk/include/mods/svc/resource.h](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/sdk/include/mods/svc/resource.h#L9-L46); [src/dusk/mods/svc/resource.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/dusk/mods/svc/resource.cpp#L20-L97).

El juego usa otro circuito: `dRes_info_c::set` crea `mDoDvdThd_mountArchive_c`, `setRes()` devuelve `1` mientras el comando no sincroniza, después construye recursos dentro de heaps. `dRes_control_c::setRes` incrementa count; `deleteRes` reduce count y llama destructor a cero. `getResInfoLoaded` puede devolver null durante lectura. En PC se reconstruye con placement-new el slot reciclado para evitar punteros residuales. **SOURCE_OBSERVED, PRES-005/006**: [src/d/d_resorce.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/d/d_resorce.cpp#L53-L69); [src/d/d_resorce.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/d/d_resorce.cpp#L601-L657); [src/d/d_resorce.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/d/d_resorce.cpp#L808-L921).

Discrepancia estática **PRES-035**: `file_exists`/`directory_exists` devuelven bool pero retornan `MOD_INVALID_ARGUMENT` (valor 5) al recibir contexto/ruta inválidos; en C++ eso se convierte a true. Validar argumentos antes de consultar, y no interpretar true como comprobación de seguridad de la ruta. No se corrigió ni ejecutó el host. [Implementación](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/dusk/mods/svc/resource.cpp#L99-L116), [enum ModResult](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/sdk/include/mods/api.h#L48-L58).

## Flujo y precedencia de overlays

Entrada `overlay/` estática o `OverlayService.add_file/add_buffer` → slots por propietario → `overlay_sync_files` en boundary del loader → registros Aurora DVD → `JKRArchive::notifyOverlayFilesChanged`. Dentro de cada mod se emiten estáticos antes de runtime; runtime se ordena por secuencia y el conjunto por active_mods. El contrato dice que la última entrada gana y distingue disco case-insensitive. No se inspeccionó la implementación interna de Aurora; la precedencia se observa aquí como orden emitido y contrato. **STATIC_CROSSCHECKED, PRES-002**: [sdk/include/mods/svc/overlay.h](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/sdk/include/mods/svc/overlay.h#L16-L29); [src/dusk/mods/svc/overlay.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/dusk/mods/svc/overlay.cpp#L70-L113); [src/dusk/mods/svc/overlay.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/dusk/mods/svc/overlay.cpp#L185-L211).

Las aperturas DVD pueden coincidir con resync: `cbOpen` toma metadata bajo mutex, y `OpenOverlayFile` conserva bytes o shared buffer para lecturas posteriores. ID desaparecido devuelve null. En archivos internos ARC, cambiar generación elimina la asociación activa pero conserva la allocation antigua; `removeAllOverlayResources` finalmente libera el conjunto. Esto protege punteros entregados previamente frente a simple cambio de generación, no frente a desmontar el archive ni a `removeOverlayResource(resource, true)` o `removeAllOverlayResources()`, que liberan allocations incluso con el archive vivo. Tampoco reconstruye un modelo ya decodificado. **SOURCE_OBSERVED, PRES-003/004**: [src/dusk/mods/svc/overlay.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/src/dusk/mods/svc/overlay.cpp#L115-L175); [libs/JSystem/src/JKernel/JKRArchivePri.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/libs/JSystem/src/JKernel/JKRArchivePri.cpp#L373-L445); [libs/JSystem/src/JKernel/JKRArchivePri.cpp](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/libs/JSystem/src/JKernel/JKRArchivePri.cpp#L515-L539).

## Integración, riesgos y rollback

`OFFICIAL_SERVICE`: ResourceService para bytes propios y OverlayService para archivos DVD; `ASSET_OVERLAY`: carpetas estáticas, incluyendo archivo dentro de ARC documentado en [docs/modding.md](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/docs/modding.md#L57-L81). `POTENTIAL_REQUIRES_VERIFICATION`: acceso C++ a dRes/JKR fuera del servicio. No certificar dirección o hook de estas funciones sin resolver símbolos/ABI. Registrar todas las handles, retirar registros propios y liberar buffers propios; después reingresar a la escena o reiniciar cuando un consumidor conserve recursos ya leídos. Esto es una precondición operativa, no garantía de rollback instantáneo: [sdk/include/mods/svc/overlay.h](https://github.com/TwilitRealm/dusklight/blob/40457c6adb381928e4b5fef6ed459ed291edd5e2/sdk/include/mods/svc/overlay.h#L16-L29).

Consumidores: modelos/materiales, HUD/fonts, partículas, stage/room y audio. Proveedores: bundle loader, DVD/Aurora, JKernel heaps. Véanse [modelos](models_animations_materials.md), [HUD](hud_ui_text.md), [audio/partículas](audio_particles_effects.md), [stages](stages_rooms_layers.md).

Pendiente: trazar scheduler DVD completo, límites de archives anidados y coexistencia real de mods; inspeccionar extern/aurora fijado; medir comportamiento al reload con recursos consumidos. No se abrieron assets del disco ni se redistribuyeron.

Cobertura: READ/CROSSCHECKED selectiva según SYSTEM_INDEX y los niveles de cada evidencia; ninguna ruta constituye prueba runtime Windows/DX12.


## CP-R25 — Ganador de overlay, lectura JKR y cache dRes

SDK-018/PRES-002..004 ya documentaron prioridad, publicación y retención de allocations. Este bloque añade un consumidor concreto y el límite de **volver a pedir un recurso**: getObjectRes no necesariamente relee el archivo. PRES-065..067 no vuelven a contar el orden emitido como descubrimiento nuevo ni certifican el selector Aurora ausente.

**Contrato y prioridad reutilizados.** OverlayService declara último ganador: runtime sobre estático dentro del mod y mod posterior sobre anterior, con path case-insensitive. El host emite esa secuencia y avisa mediante notifyOverlayFilesChanged. claim_overlay_path solo registra/advierte reclamaciones; no rechaza conflicto ni mezcla contenido. El ganador efectivo de DVD se delega a Aurora. No se afirma que coexistencia de dos reemplazos produzca datos compatibles, ni se extiende el orden a hooks, BST o servicios con otra política.

**Consumidor nuevo (PRES-065).** JKRArchive::getIdxResource busca una entrada existente y llama fetchResource virtual. En JKRMemArchive, TARGET_PC consulta getOverlayData **antes** de retornar JKAR_DATA de la entrada. Si existe overlay activo válido, usa sus bytes; si no, intenta apertura, allocation alineada y lectura de la ruta interna correspondiente. Tamaño fuera de límite, allocation nula, fallo de apertura o lectura que no devuelve tamaño lógico exacto hacen retornarNULL. El fetch del archive entonces usa backingARC y su cache normal. Esa ruta fuente no selecciona explícitamente el overlay del mod anterior: sería incorrecto prometer fallback entre mods sin leer Aurora. Tampoco valida el formato del contenido obtenido.

La sobrecarga de copia usa copyOverlayData y copia min(tamaño overlay,capacidad), comunicando cantidad copiada; éxito no demuestra copia completa ni que un recurso truncado pueda decodificarse. La consulta de tamaño por puntero de overlay usa la allocation registrada, no reinterpreta ese puntero como datos del ARC original. Se estudia JKRMemArchive; no se universaliza a Comp/ARAM/DVD archives.

**Segundo nivel: cache del juego (PRES-066).** loadResource de dRes_info reserva mRes, obtiene cada entrada vía getIdxResource y transforma según tag. Por ejemplo BMDR/BMDV/BMDE/BMWR/BMWE pasan por loaderBasicBmd y BTK/BTP/otros por loader de animación; luego guarda el resultado en mRes[fileIndex]. No se repite el análisis de modelo/animación CP-R11. El resultado puede ser objeto decodificado o bytes según clase, no una promesa de copia profunda.

getObjectRes por índice/nombre resuelve el dRes_info ya cargado y termina en getRes, cuyo acceso es al array mRes. Ese camino no llama de nuevo a getOverlayData ni comprueba generación. notifyOverlayFilesChanged únicamente incrementa el contador JKR; no recorre dRes ni reconstruye sus objetos. Así quedan separados registro ganador, nueva apertura, allocation JKR, objeto decodificado y puntero entregado al actor.

| Tras retirar/cambiar ganador y publicar nueva tabla | Resultado sustentado |
| --- | --- |
| Volver a getObjectRes con el mismo dRes_info cargado | Sigue entregando mRes existente; no provoca relectura por sí mismo. |
| Volver a getIdxResource en JKRMemArchive | Consulta generación/overlay nuevamente; puede obtener otros bytes o fallbackARC. |
| Conservar puntero previo a bytes overlay tras cambio de generación | JKR conserva allocation mientras siga owned, según PRES-004; no actualiza su contenido automáticamente. |
| removeResource(resource) / removeAllOverlayResources / teardown | Pueden liberar allocation; retención por generación no protege esos usos. |

**Fallo, limpieza y reversión.** Retirar registro owned marca dirty y el frameEnd publica tabla; lifecycleApplied también sincroniza. Aplicación no significa que el consumidor vivo haya adoptado el nuevo ganador. Cuando count de dRes llega a cero se invoca destructor; este contempla comando pendiente o archive, deleteArchiveRes y destrucción de heap/unmount bajo sus condiciones. No todos los arcos ni referencias desaparecen por quitar un handle. No se debe liberar el backing/heap ni reconstruir el cache mientras actores/modelos lo presten sin conocer su ciclo de vida.

**Inferencia condicionada (PRES-067).** Si cambia ganador y se conserva el mismo dRes_info, una nueva lectura JKR puede coexistir con mRes anterior: no hay un swap transaccional de todos los consumidores. Que el siguiente candidato sea visible en nueva apertura depende del contrato de orden y del backend; se mantiene pendiente su prueba. Una lectura fallida de overlay puede caer a bytes originales en este consumidor, sin evidenciar que el contenido malformado se detecte antes de decodificarlo. No se ejecutó resync, archivo ni coexistencia Windows.

**Frontera .dusk.** OverlayService es OFFICIAL_SERVICE; carpeta estática es ASSET_OVERLAY; ResourceService conserva contrato de bytes propios distinto. Los símbolos JKR/dRes nuevos son localizadores POTENTIAL_REQUIRES_VERIFICATION. Rollback de registro no es rollback de mRes ni de efectos de gameplay ya consumidos. Q-14 pasa a PARCIAL solo por esta política/consumidor; conflictos de hooks y coexistencia real siguen pendientes. No se propone invalidar caches ni añadir una API al host.
