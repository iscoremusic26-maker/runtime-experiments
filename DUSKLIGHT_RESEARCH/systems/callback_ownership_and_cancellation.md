El hallazgo es que una operación de retirada no tiene semántica uniforme entre servicios.

Estas consecuencias se deducen del control y de las copias observadas, no de una prueba de reentrancia. No se afirma que el host descargue una DLL en mitad de ese callback, ni que los tres métodos puedan llamarse desde cualquier hilo. Save documenta callbacks en el game thread; las fuentes Host/Camera revisadas no justifican uso concurrente arbitrario.

Los consumidores conectan el dispatch con operaciones reales: Save notify sigue a `save_slot_loaded`, `save_slot_new` y `save_slot_written`; `modules_mod_detached` se llama desde el teardown del loader; los operadores de cámara se consultan desde `dCamera_c::Run`. ## Uso desde .dusk y rollback

Las operaciones son **OFFICIAL_SERVICE**. Las funciones internas se indexan para localizar implementación, sin certificar su export ni recomendarlas como targets de hook. Un consumidor debe conservar userdata mientras pueda alcanzarlo un dispatch ya iniciado; en particular, no inferir que SaveService.unobserve_saves permite liberar inmediatamente el storage si otro callback de la misma notificación todavía lo referencia. El riesgo de pointer vencido bajo ese supuesto es **STATIC_INFERRED**, sin fallo observado (CALLBACK-004).

Retirada de registro, invalidez de handle, fin de callbacks, liberación de userdata y descarga de código son hitos distintos. Respetar la fase del servicio, invalidar el estado lógico propio y liberar storage solo al demostrar que no queda un dispatch pendiente. La fuente no proporciona aquí una barrera universal de callbacks ni una API genérica para drenar todos los servicios.

Pendiente mínimo: inspeccionar una ruta adicional (ItemService o MessageService) antes de extender esta matriz; resolver el contrato de llamadas reentrantes de cada servicio y confirmar las garantías de release de callbacks. Cualquier validación runtime futura debe delimitar revisión, plataforma y secuencia concreta; este encargo sigue siendo investigación documental.
