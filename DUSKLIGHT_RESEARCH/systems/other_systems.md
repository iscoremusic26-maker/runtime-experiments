Si una futura extensión altera un modo, deberá deshacer su propio estado y dejar completar el cleanup del actor; quitar un hook no repone switches/posiciones de un puzzle que ya avanzó (PLAYER-028/029/030/033). ## CP-R14 — presión, background callback, switch y recarga

Cadena representativa del actor original `daObjSwpush::Act_c`; no arquitectura universal de puzzles/NPC. **Contrato/ubicación — PLAYER-035:** profile current-layer/list2,fopAc wrapper. Parámetros extraen tipo/model/evento/switch/couple; copia angleZ a mPrmZ para switch2 y borra inclinación Z. Tipo4 fuerza modelo1,modelo15 pasa0; no se ve validación general de todos los índices de las tablas. Modelo y dBgWSv se construyen en solid heap tras resLoad COMPLEATE. Regist true indica error,al igual que fallo de heap lleva ERROR. Solo en éxito se instala rideCB y se inicializan estados/altura según flags y switches. No repetir construcción J3D de CP-R11. Layers determinan colocación,pero switches usan home room,no un bank por layer automático.

**Evento real — PLAYER-036:** Acch GroundCheck obtiene suelo,corrige posición y,con sus gates/field_0xc0,invoca dBgS::RideCallBack(poly,m_my_ac). El dispatcher usa índice del fondo registrado y pasa actor dueño almacenado + actor visitante a dBgW::CallRideCallBack; este llama función registrada de forma sincrónica. rideCB recibe bgw/dueño/visitante; exige status fopAcStts_FREEZE_e (no interpretar su nombre como regla semántica de inmovilidad),prueba dos triángulos y couple opcional. Usa margen distinto según mPrevRiding. Clasifica carry-type1 como modo2 y otros modo1; Link puede fijar vibración y heavy boots→mHeavyRiding. Couple acumula bits ALINK/NPC_P2 y exige ambos. No guarda el puntero visitante; dueño/background son prestados por registro. Múltiples contactos pueden sobrescribir mRidingMode,no es máximo universal de peso. La fase exacta depende de cuándo el visitante ejecute Acch; no se prueba un orden global entre todos los profiles.

**Debounce/estado — PLAYER-037:** set_push_flag incrementa contadores hasta umbral y mantiene/decrementa al desaparecer contacto. Separa mMiniPushFlg de mPushFlg pesado; able_ride_time_middle prolonga contacto modo2. Luego MODE_UPPER puede iniciar descenso por presión o para obedecer switch. mChangingState solo marca una mutación propia por presión; al llegar mCurHFrac<=0,MODE_U_L invierte switch si toggle,o pone ON/OFF según ON_IS_UP,si changingState. No se escribe switch en cada rideCB. MODE_LOWER decide volver por ausencia,STAY_PRESSED,OBEY_SAVE y switch2/FLAG_UNK20; toggle no revierte automáticamente al soltar. Al llegar arriba solo escribe si changingState. No inventar semántica de FLAG_UNK20. Rama REQ_HEAVY existe,pero las cinco entradas M_attr examinadas no fijan ese flag; presencia de código no prueba una colocación original pesada.

Mthd_Execute: demo dispatcher→set_push_flag→mode dispatcher→calc_top_pos→copiar prev/limpiar riding/heavy/couple→matriz→CopyBackVtx→modificar cuatro vértices→Move. calc_top_pos separa respuesta visual de altura colisión mediante retardo. Dos controles de mDebounceTimer en mode_upper pueden decrementarlo dentro de una misma ejecución; no traducir constante30 a segundos ni treinta ticks garantizados. Eventos de demo se solicitan/reintentan según aceptación y se resetean al terminar; la máquina de modo sigue después del dispatcher demo en este execute,no se demuestra que la escritura exija aceptar todo evento. Joint callback usa userArea del modelo para desplazar dibujo; el objeto conserva estado de geometría,visual y switch distintos.

**Switch/consumidor/recarga — PLAYER-038:** on/off/rev/is_switch delegan con fopAcM_GetHomeRoomNo a dSv_info_c. ID selecciona mMemory,mDan,mZone/one-zone;255 no opera. No clasificar automáticamente todo switch del actor como persistente de room: depende del ID y banco,según WORLD-015/016. Estas funciones escriben RAM,no serializan CARD. El propio create vuelve a leer ambos switches para fijar altura: toggle puede iniciar arriba aun con bit activo. Como consumidor independiente de la misma API genérica,Lv6Lblock ya contrastado en PLAYER-033 detecta cambio y mueve bloque; NO se ha probado que una colocación concreta comparta ID/room con este swpush. Spinner/Lv6Lblock comparten dependencia switch→máquina→geometría; difieren evento de entrada,de momento de escritura y reglas latched. Deshacer una flag no reconstruye inmediatamente colisión/animación ni confirma persistencia en disco.

**Cleanup/error — PLAYER-039:** Delete llama Release(mpBgW),registra error si true,y sigue resDelete devolviendo1. Release válido quita entrada de tabla y owner,retira bgw;NULL retorna error sin desreferenciar. En error de registro/create parcial no asumir callback instalado ni rollback completo. Wrapper fopAc_Delete,tras retorno exitoso,retira muestras interp/colas y destruye heap; proceso de creación cancelada intenta Delete (ARCH-007). Quedan pendientes todos los fallos de alloc/registro y garantías con contacto en curso: Release no es una barrera universal de llamadas,ni Delete1 demuestra que todas las operaciones previas tuvieron éxito. No hay limpieza explícita de switches en este Delete.

**Frontera .dusk:** ActorService para lifecycle/creación propia y StageService para edición de colocación al cargar (SDK-001/WORLD-004/005); no son APIs universales de presión o switches vanilla. Resource/overlay solo dentro del contrato de recursos. Lógica interna y callback son POTENTIAL_REQUIRES_VERIFICATION,sin firma binaria/target Windows probados. Estado pertenece al actor,background al registro+heap,y switch al banco del juego. Rollback de registros propios no revierte progreso ni garantiza reload de consumidores vivos. Q-12 sigue parcial; otros puzzles/NPC/bosses/minijuegos no se elevan por este caso.
